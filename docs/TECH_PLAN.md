## 2. Dependencies

```
fastapi              # API layer
uvicorn              # ASGI server            [installed]
pydantic>=2          # schema contract        [installed]
sentence-transformers# bge-small-en-v1.5 encoder
rank-bm25            # lexical retrieval
numpy                # cosine + RRF           [installed]
httpx                # Ollama client          [installed]
pytest, pytest-benchmark
```

Missing on host: `fastapi`, `sentence-transformers`, `rank-bm25`.

Deliberately **not** used:

| rejected | reason |
|---|---|
| FAISS | N ≈ 121 cache vectors, 578 catalog entries. A numpy matmul is faster than an ANN index at this scale and adds no build step or recall cliff. |
| SQLite / Redis | No mutable state at runtime. The plan library is a read-only committed artifact. |
| LangChain / LlamaIndex | The pipeline is five deterministic stages with one constrained model call. A framework adds indirection over ~400 lines of logic and obscures the latency budget. |

Lockfile committed (`requirements.lock`, generated by `uv pip compile`).
Public PyPI only. `make venv` installs from the lock, not the loose spec.

## 4. Model roster

### 4.1 Build tier (offline, quality-optimized)

Hosted: Gemini or GPT-4o-mini. No latency constraint, runs once, output is frozen into `artifacts/`. Key supplied via `SECRET_*` env var, never committed.

### 4.2 Runtime tier (cold path, latency-constrained)

Hard requirement: fits in 7.5 GiB VRAM **and** produces ~150 constrained-JSON tokens in < 4 s.

| model | size | verdict |
|---|---|---|
| `gemma3:4b-it-q4_K_M` | ~3.3 GB | **primary.** Fits with headroom; Gemma is explicitly encouraged by the organizers. |
| `qwen2.5:7b-instruct-q4_K_M` | ~4.7 GB | accuracy comparison; strong at structured output |
| `qwen2.5vl:7b` | 6.0 GB | *already installed*; vision-tuned, used only for the throughput baseline |
| `gemma4:26b` | 18 GB | ❌ **exceeds VRAM.** Would spill to CPU and blow C7. Installed but unusable here. |
| `gemma4-claude:latest` | 18 GB | ❌ same |

**Action M0-2:** `ollama pull gemma3:4b-it-q4_K_M`, then re-run the benchmark warm.

### 4.3 Constrained decoding

Ollama's `format` parameter accepts a JSON Schema and applies grammar-constrained decoding. The Stage 2 skeleton (`ARCHITECTURE.md` §7.2) is passed as that schema, which makes unparseable output structurally impossible and removes an entire class of repair work.

Request template:

```json
{
  "model": "gemma3:4b-it-q4_K_M",
  "format": { /* Stage-2 skeleton JSON Schema */ },
  "stream": false,
  "keep_alive": -1,
  "options": { "temperature": 0, "top_k": 1, "seed": 42, "num_predict": 400 }
}
```

`keep_alive: -1` pins the model in VRAM. The measured 12.9 s cold load must never land on a request.

## 5. Build pipeline

```bash
make build      # scripts/compile_plans.py → artifacts/
make serve      # uvicorn api.main:app
make bench      # scripts/bench.py  → docs/metrics.md §3
make batch      # scripts/run_batch.py → results.jsonl
make test       # pytest
```

`make build` steps:

1. Load `deeplinks.json`; build BM25 + dense catalog index → `catalog_index.pkl`.
2. Deduplicate `siis_responses.json` → 11 distinct documents.
3. For each document: segment → extract (hosted LLM) → resolve deeplinks → assemble → validate → repair. **Fail the build on any unresolved blocking gate.** A dirty artifact must never ship.
4. Generate 8–10 `query_variations` per plan.
5. Embed canonical query + all variations → `cache_vectors.npy` (~121 × 384 float32).
6. Write `plan_library.json`, `cache_manifest.json`.

The build is reproducible: same inputs + same seeds → byte-identical artifacts. CI asserts this.

## 6. Test strategy

| layer | scope | gate |
|---|---|---|
| Unit | each validator gate G0–G16, in isolation | 100% of gates covered |
| Data pinning | the facts table in `DATA_CONTRACT.md` §8 | exact match |
| Golden | Appendix B example reproduced field-for-field | exact match |
| Deeplink regression | **~40 hand-labelled (step text → expected catalog id) pairs** | precision@1 tracked; this is the tuning set for `TAU_LINK` |
| Paraphrase | held-out paraphrases not used as cache seeds | hit rate ≥ 80% |
| Adversarial | prompts engineered to induce `samsung.com/support` | zero leaks |
| Determinism | same input × 5 runs | byte-identical |
| Perf | N ≥ 30 per path | P95 hot ≤ 300 ms, cold ≤ 8 s |

**The deeplink regression set is the single highest-value test asset.** Both threshold decisions (`TAU_LINK`, `TAU_HIT`) are calibrated against labelled data rather than eyeballed. Build it in M2, by hand, from the 11 SIIS documents.

Paraphrase honesty rule: a variation used as a cache seed cannot also score the hit rate. Hold out a disjoint set, authored independently.

## 7. Milestones

Dependency-ordered. Critical path marked ★.

### M0 — Environment (½ day) ★
- Pin Python 3.12 via `uv`; install missing deps; commit `requirements.lock`.
- Start the `ollama` toolbox; `ollama pull gemma3:4b-it-q4_K_M`.
- Re-benchmark **warm** with `keep_alive: -1`; record real prompt-eval and generation rates.
- `git init`, vendor `schema.py` and the data files unmodified.

**Exit:** warm benchmark recorded; ~150 output tokens generate in < 4 s.

### M1 — Validators first (2 days) ★
Build the scoreboard before the system.
- Implement G0–G16 (`DATA_CONTRACT.md` §7) with unit tests.
- Run them against Appendix B (must pass) and `sample_output.json` (**must fail G6** — proves the gate works).
- Data-pinning tests.

**Exit:** `make test` green; a CLI that scores any candidate JSON.

### M2 — Deeplink resolution (3–4 days) ★
- Catalog index: BM25 + bge-small, RRF fusion.
- Polarity gate, appliance denylist, corrupt-entry handling.
- Hand-label ~40 step→deeplink pairs.
- Sweep `TAU_LINK`; record the precision / dummy-rate trade-off curve.

**Exit:** precision@1 on the labelled set recorded; `TAU_LINK` chosen from the curve, not by default.

### M3 — Extraction (4–5 days) ★
- `segment.py`: SIIS → numbered candidates with heading structure.
- Stage-2 constrained-decode prompt + JSON Schema.
- Index→text expansion, imperative normalization, the repair loop.
- Run over all 11 documents; manual quality review against the source text.

**Exit:** 11 plans pass every blocking gate; zero steps traceable to anything outside the source.

### M4 — Cache and compilation (2–3 days) ★
- `compile_plans.py` end to end.
- Variation generation; embed and index.
- Author a disjoint held-out paraphrase set; sweep `TAU_HIT`.

**Exit:** hit rate ≥ 80% on held-out paraphrases; artifacts reproducible byte-for-byte.

### M5 — API (2 days) ★
- FastAPI, both endpoints, the `meta` block, both fallbacks.
- `/health` gated on all four subsystems.
- Token/cost accounting on the cold path.
- `bench.py`, N ≥ 30 per path.

**Exit:** P95 hot ≤ 300 ms, cold ≤ 8 s, measured and recorded.

### M6 — Generalization (3–4 days)
The largest scoring risk: all 20 public queries are **Display**; the hidden set spans Battery, Camera, Performance.
- Hand-author probe queries for the three unseen domains.
- Source or write representative SIIS-style text for them.
- Audit every module for display-specific assumptions (keyword tables, denylists, topic templates).
- Wire the read-only diagnostics `DL-0474`/`0475`/`0476` (Diagnose Battery Drain / Slow Performance / Overheating) as validation candidates.

**Exit:** the pipeline produces valid plans in all four domains.

### M7 — Ablation and reporting (2–3 days)
PDF Appendix C requires an ablation table. Three variants, same test set:

| variant | description |
|---|---|
| Baseline | full LLM deeplink mapping — model picks URIs directly |
| A | hybrid BM25 + dense retrieval (**our design**) |
| B | pure rules-based mapping — keyword tables only |

Record step accuracy (0–3), deeplink relevance (0–2), P95 latency, cost/query for each.

Expected finding, to be confirmed rather than assumed: Baseline scores worst on catalog integrity (it hallucinates URIs); B is fastest but brittle on paraphrase; A wins overall. **Report what we measure, including where A loses.**

**Exit:** `docs/metrics.md` complete per the Appendix C template.

### M8 — Packaging (1–2 days)
- `Containerfile`; vendored encoder weights; cold-start measured.
- `submission.yaml`; `run_batch.py` → `results.jsonl`.
- Secret hygiene audit; full clean-clone rebuild.

## 8. Reporting

`docs/metrics.md` follows the PDF Appendix C template verbatim: schema/rule compliance, accuracy benchmarks, latency percentiles (N ≥ 30/path), cost and cache efficacy, the ablation table, and known limitations.

Populate it from `make bench` output rather than by hand, so it cannot drift from the code.

§6 of that template ("Known Edge Cases & System Limitations") is a scoring opportunity, not a confession. Document the catalog coverage holes, the Display-only training data, and the multi-intent policy — with evidence. An honest, specific limitations section reads as rigour.

## 9. Anti-hardcoding posture

The hackathon reviews high-scoring submissions manually: *"aces the public set but collapses on re-skinned hidden scenarios is reviewed manually for hardcoding."*

Our cache is a pre-warmed artifact, which PDF Phase 3 explicitly mandates. The line not to cross is hand-authoring its contents. Rules:

1. Everything in `artifacts/` is generated by `compile_plans.py`. **Never edit an artifact by hand** — fix the pipeline and rebuild.
2. No lookup keyed on query id, row id, or exact query string.
3. The cold path must produce an acceptable plan for a document the build never saw. Tested in M6.
4. `make build` from a clean clone reproduces `artifacts/` byte-for-byte. CI asserts it.

If we ever want to "just fix this one plan", that is the signal the pipeline is wrong.
