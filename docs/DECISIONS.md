# Decision Record & Open Questions

ADRs carry the reasoning; `ARCHITECTURE.md` carries the design. When revisiting a choice, read the ADR first — the constraint that forced it is usually still there.

---

## ADR-001 — The LLM emits step *indices*, not step text

**Status:** accepted · **Drives:** C4, C7

**Context.** Two independent problems. (a) PDF §4.2.3 forbids steps not present in the reference text; prompting alone does not reliably prevent invention. (b) Measured throughput on the RTX 4060 is **43.5 tok/s**; a full generated plan is ~800 output tokens ⇒ ~18 s, against an 8 s budget.

**Decision.** Deterministic code segments the SIIS document into numbered candidate steps. The model returns `"steps": [7, 8]` — indices. Code expands indices to the verbatim source sentences.

**Consequences.**
- A step that is not in the source cannot be expressed. C4 becomes structural, not aspirational.
- Output drops to ~150 tokens ⇒ ~3.4 s. C7 met with ~3 s margin.
- Cost: step wording is bounded by the source's phrasing. Where SIIS prose is clumsy, our steps inherit it. Mitigated by deterministic imperative normalization, not by regeneration.
- Cost: poor segmentation caps plan quality. `segment.py` becomes a high-value test target.

**Rejected:** full-text generation with a post-hoc similarity check against the source — slower, and "similar enough" is a threshold we would have to defend to a judge.

## ADR-002 — The LLM never sees or emits a URI

**Status:** accepted · **Drives:** C3

**Context.** PDF §4.2.2 forbids hallucinated or altered URIs; §7.4 notes the identifiers are opaque tokens, so matching must run on descriptive metadata.

**Decision.** The model emits a natural-language screen descriptor. A deterministic hybrid retriever resolves descriptor → catalog entry. G9 additionally asserts every emitted URI is a catalog member.

**Consequences.** URI hallucination is impossible by construction. Resolution quality becomes a retrieval-tuning problem with a labelled test set (M2) rather than a prompting problem.

## ADR-003 — Pre-warmed cache compiled by the same pipeline

**Status:** accepted · **Drives:** C6, C8, C9

**Context.** 20 public queries collapse to **11 distinct SIIS documents**. A plan is a function of the document, not the query string. PDF Phase 3 mandates "persistent local caching with pre-computed query variations"; §5 says an omitted `siis_response` performs lookup "against pre-warmed cache entries."

**Decision.** Run the full pipeline at build time over all 11 documents; freeze the results into `artifacts/`. Runtime hot path does normalize → embed → cosine → return, with no model inference.

**Consequences.**
- Hot path ~15 ms against a 300 ms budget; `cost_usd` genuinely 0.0.
- Determinism by construction, not by prompt discipline.
- **Risk:** superficially resembles hardcoding. Mitigated by the invariant that artifacts are *only* ever generated by `compile_plans.py`, never hand-edited, and reproducible byte-for-byte from a clean clone (TECH_PLAN.md §9). The distinction that matters to a reviewer: a pre-warmed cache is generated by the same code that serves cold queries; a lookup table is not.

## ADR-004 — `query_variations` double as cache seeds

**Status:** accepted · **Drives:** C8

**Context.** PDF §4.1 requires 8–10 paraphrases across varied registers; §6.2 requires ≥80% hit rate on unseen paraphrases. These look like separate requirements.

**Decision.** Embed every generated variation and index it alongside its canonical query. One artifact satisfies both.

**Consequences.** Hit rate scales with variation diversity, so register coverage (formal / casual / keyword-only / frustrated / typo-inclusive) is a *retrieval* concern, not a cosmetic one.

**Test integrity rule.** A variation used as a cache seed must never score the hit rate. The held-out paraphrase set is authored independently and kept disjoint. Violating this produces a number that looks excellent and means nothing.

## ADR-005 — Polarity gate as a hard pre-filter

**Status:** accepted · **Drives:** deeplink relevance (0–2)

**Context.** PDF §6.2 scores exact target screen versus parent menu. The catalog is full of near-duplicate pairs distinguished only by direction — `DL-0020`/`DL-0021` (disable/enable adaptive brightness), `DL-0095`/`DL-0096` (Edge panels). Embeddings place these pairs almost on top of each other; "enable X" and "disable X" are semantically near-identical to an encoder.

**Decision.** Derive intent from the descriptor's leading verb and hard-filter on `originalType` **before** ranking: enable→`onURL`, disable→`offURL`, set→`updateURL`, open→`onClickURL`.

**Consequences.** Removes the retriever's single worst failure mode for near-zero cost. Cost: a mis-derived verb yields *no* candidate rather than a wrong one — which degrades to `dummy_positive`, an acceptable failure.

## ADR-006 — Brute-force cosine, no ANN index

**Status:** accepted

**Context.** N ≈ 121 cache vectors, 578 catalog entries, 384 dims.

**Decision.** One `numpy` matmul over a single float32 matrix.

**Consequences.** Sub-millisecond, exact (no recall cliff), no index build step, one less dependency. Revisit only above ~50k vectors — roughly 400× the current corpus.

## ADR-007 — Enforce the PDF's rules over the shipped sample

**Status:** accepted, **pending mentor confirmation (M-Q2)**

**Context.** `sample_output.json` violates PDF §4.1: its `description` fields are 9 and 12 words against a stated 5–7. Appendix B complies (7 words).

**Decision.** Enforce the PDF. Gate G6 rejects the shipped sample, and a test asserts that rejection.

**Consequences.** If graders score against the sample rather than the spec, this is wrong and cheap to invert (one constant). Flagged to the mentor. Documented in `metrics.md` §6 either way.

## ADR-008 — One Goal per distinct SIIS document

**Status:** accepted

**Context.** `contexts` is `List[Goal]`. `input.txt` row 17 bundles three symptoms: cracked at the fold, touch dead in places, can barely see.

**Decision.** Emit one Goal per distinct matched document, sorted by `score` descending. Row 17's three symptoms share one root cause and one document (*Cracked or bleeding screen*) ⇒ **one** Goal.

**Consequences.** Multi-goal output occurs only when retrieval genuinely matches separate documents above threshold. Per-symptom splitting would emit near-duplicate plans from a single source and read as the fragmentation PDF §7.2 warns against.

## ADR-009 — Local model on the runtime cold path

**Status:** accepted · **Supersedes:** an earlier hosted-runtime option

**Context.** The `ollama` toolbox exists with a working CUDA runner on an RTX 4060 (7.5 GiB usable). The build tier is hosted; the runtime tier need not be.

**Decision.** Hosted model at build time (quality), local `gemma3:4b-it-q4_K_M` at runtime (latency, cost, no network dependency at eval time). Gemma also aligns with the organizers' stated encouragement.

**Consequences.**
- No network or API key needed at evaluation time; `cost_usd` is honestly 0.0 on every path.
- **Risk:** the two tiers can diverge structurally, so the hidden-set cold path would behave unlike the demo. Mitigated because neither model is trusted with formatting or URIs — both emit only the Stage-2 skeleton, and identical deterministic code does everything else.
- **Discipline:** test the cold path with the *local* model from M3 onward. Never demo hosted and ship local untested.
- `gemma4:26b` (18 GB) is installed locally but **exceeds VRAM** and cannot serve this path.

## ADR-010 — Validators before engine

**Status:** accepted

**Context.** Scoring is dominated by automated gates (schema conformance, zero leakage, catalog validity, latency, hit rate). PDF §7.5 names prompt-only constraint enforcement as a pitfall.

**Decision.** M1 builds G0–G16 and a scoring CLI before any extraction code exists.

**Consequences.** Every later milestone has an objective pass/fail signal from day one, and the repair layer has a specification to code against rather than a vibe.

## ADR-011 — Ranking and confidence are separate functions

**Status:** accepted · **Supersedes:** thresholding on the RRF score

**Context.** The first resolver thresholded on the fused RRF score. Every query
returned exactly `1/(60+1) = 0.0164` and fell to `dummy_positive`: RRF is
rank-derived, so the winner scores identically no matter how good the match is.
Measured precision was 11.6%.

**Decision.** Rank with RRF; compute confidence separately from absolute signals
on the winning candidate — rescaled cosine, token-stem coverage, and a polarity
term.

**Consequences.** Precision on catalog-register descriptors went 11.6% -> 100%.
Thresholds are now calibratable, which RRF scores never were. `scripts/calibrate.py`
derives the cosine band from labelled data rather than guessing it.

## ADR-012 — Polarity is a prior, not a gate

**Status:** accepted · **Supersedes:** the hard `originalType` filter in ADR-005

**Context.** ADR-005 made polarity a hard pre-filter. Measurement showed it
*excluding correct answers*: "turn on smoother scrolling" resolves to DL-0228, an
`updateURL`, and "turn off usage sharing" only exists as DL-0083, an
`onClickURL`. The catalog does not always offer the entry type the phrasing
implies.

**Decision.** Keep polarity as a rank bonus and a confidence term. Only appliance
noise and read-only (`originalType: null`) entries remain hard filters.

**Consequences.** Lexical precision@1 reached 100% (38/38) with 100% dummy
correctness. The near-duplicate disambiguation ADR-005 wanted is retained; the
false exclusions are gone.

## ADR-013 — Two-factor cache acceptance

**Status:** accepted · **Drives:** C8

**Context.** A single similarity threshold cannot meet both targets. Measured:
tau=0.70 gives 88.5% hit rate but 16.7% false hits on out-of-domain queries;
tau=0.78 gives 0% false hits but only 76.9% hit rate, under the >=80% requirement.
The curves cross.

**Decision.** Accept when similarity >= 0.80 outright, or when similarity >= 0.70
**and** the margin over the best *other* plan is >= 0.04. Out-of-domain queries
are weakly similar to every plan (margin median 0.011) where real paraphrases
have a clear winner (margin median 0.102).

**Consequences.** 84.6% hit rate at 8.3% false hits, beating both single-threshold
points. One residual false hit ("extremely slow and laggy" -> Touchscreen issues)
is semantically adjacent and is reported rather than tuned away.

## ADR-014 — Multi-probe screen resolution

**Status:** accepted · **Drives:** deeplink relevance on the cold path

**Context.** The local extractor reliably puts the *parent menu* in `screen`
("display settings", "general management") and the *specific feature* in `name`
("enable touch sensitivity"). Parent-menu matching is the exact failure PDF
section 6.2 penalises. With `screen` alone, 0 of 8 cold-path auto actions
resolved to a catalog entry.

**Decision.** Probe `name`, `screen`, and `name + screen`; keep the most
confident result. Also make `screen` a *required* schema field with `""` as the
explicit "no screen" answer, since optional fields were silently omitted.

**Consequences.** Cold-path auto actions carrying a catalog deeplink went
0% -> 65%. The system no longer depends on the model's field discipline, which is
the right posture for a swappable local extractor.

## ADR-015 — Jev measured, not adopted

**Status:** rejected for the submission · **Measured:** 2026-09-21 · **Drives:** deeplink relevance, C9

**Context.** TypeSafe's Jev is a non-generative decision model: you supply options,
it returns a calibrated distribution. Our worst-measured component is exactly a
"choose among K candidates" problem — retrieval puts the correct entry in the top 5
for 87% of free-form descriptors but ranks it first only 66.7%.

**Measured** (63 labelled descriptors, Jev `choice` over our top-8 candidates):

| set | shipped baseline | + Jev rerank |
|---|---|---|
| Free-form paraphrase (20) | 30.0% overall | **80–85%** overall |
| Catalog-register (43) | 100% overall | 97.7–100% overall |

Adding an explicit `none_of_these` option — per the TypeSafe skill's "include a
no-match outcome" guidance — was what made abstention work: intended-dummy accuracy
went 0/5 to 4/5 with no threshold tuning at all. A separate presence `noul` was
unreliable (0.55 on a case whose answer was present).

Cost: 63 calls, 47.9K input / 8.7K output tokens, ~1.06 s per call.

**Decision.** **Do not adopt.** Keep the harness behind `PRISM_RERANK=off` as an
evaluated ablation variant; ship the local deterministic resolver unchanged.

**Why the measured gain does not reach us.** The +50pp is entirely in the
*free-form* descriptor regime. Our two tiers sit on opposite sides of that line:

| tier | descriptor style | baseline | + Jev |
|---|---|---|---|
| Build (`build/skeletons.json`, authored in catalog register) | catalog-register | **100%** | 97.7–100% |
| Runtime cold path (local extractor emits parent menus) | free-form | 66.7% | 80–85% |

The build tier already resolves at 100%, so Jev adds nothing where it would be
*permitted* to run; the regime where it helps is the runtime cold path, where it is
disqualified on determinism, latency and network dependency. An earlier revision of
this ADR recommended build-tier adoption; that was wrong, and the table above is why.
The cold path is better served by ADR-014's multi-probe (0% -> 65%, free and
deterministic) and, if more is wanted, a local deterministic reranker at the same
`candidates()` seam.

**Consequences.**
- The accuracy gain is captured permanently in the frozen artifacts.
- **Jev is not deterministic.** Five identical runs of "turn on auto-rotate screen"
  returned DL-0461 three times and `none` twice; confidence drifts run-to-run even
  where the pick is stable (0.62/0.65/0.66/0.70). This contradicts a widely repeated
  community claim of determinism and would violate PDF §6.1 on the runtime path.
  At build time it is harmless: output is frozen and
  `test_compiled_artifacts_are_reproducible` guards the artifacts.
- Instability concentrates at confidence 0.44–0.48, at the docs' own 0.5 abstain
  boundary; the saturated case (confidence 1.0) was stable across all runs. Applying
  the documented `<0.5 → abstain` band is therefore both the recommended policy and
  a non-determinism mitigation.
- Latency (~1.06 s/call) is 77x our 13.7 ms hot path, so it could never serve Stage 1.
- Hosted-only, no published weights: putting it on the runtime path would add a
  network dependency at grading time, which ADR-009 exists to avoid.

## ADR-016 — Emit `meta.tokens`, behind a switch

**Status:** accepted, pending M-Q3 · **Drives:** C-cost (PDF §6.3)

**Context.** §6.3 requires "tracking token utilization and inference cost per
query", and Appendix C §4 derives cost as `(prompt tokens + completion tokens) x
rate`. Appendix B's reference envelope, however, shows `meta` with exactly four
keys and no token field. `cold.py` computes the counts; the API was dropping them.

**Decision.** Emit `meta.tokens.{prompt,completion}`, controlled by
`PRISM_META_TOKENS` (default on).

**Consequences.**
- §6.3 is satisfied directly in the response rather than only in a report.
- `meta` is demonstrably not a closed set: `fallback` is mandated by §4.2.3 and is
  likewise absent from the Appendix B example, so a strict four-key reading is
  already untenable.
- Additive keys cannot break a consumer that reads the four documented ones.
- **Risk:** if a grader validates `meta` strictly, the extra key could fail a
  check. Mitigated by the switch — `PRISM_META_TOKENS=0` restores the Appendix B
  shape with no code change, which is why this is a setting and not a constant.
